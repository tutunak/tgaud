The behaviour to carry over unchanged (from echopan's CLAUDE.md and workflows):

- `ci.yml` runs on `pull_request` to `main` only. Test jobs first; then `publishing` (needs every test job,
  `packages: write`, logs in to ghcr.io with `GITHUB_TOKEN`) builds and pushes the image tagged with the full
  40-hex git **tree** hash of the checkout (on `pull_request` that is GitHub's merge ref, the tree `main` gets if
  the PR is merged as it is). An image whose tag the registry already has isn't built again; when the registry
  can't say (an error other than not found) the job stops.
- `release.yml` runs on every push to `main`: no tests, no build. It computes the tree hash of the commit, stops
  naming the image when it lacks that tag, picks the version (the `X.Y.Z` tag already on the commit, so a re-run
  bumps nothing; else the highest `X.Y.Z` on the remote plus one patch; `1.0.0` when there is none; plain `X.Y.Z`,
  no `v`), adds it to the image at the manifest level (`docker buildx imagetools create`: no pull, same digest),
  and only then pushes the git tag. `concurrency: {group: release, queue: max}`, never `cancel-in-progress`, and
  the `.github/actionlint.yaml` ignore for `queue` as echopan has it.
- Actions at the same pinned majors echopan uses (`actions/checkout@v7`, `docker/login-action@v4`,
  `docker/setup-buildx-action@v4`, ...). Top-level `permissions: contents: read`, raised per job as echopan does.

## What differs for tgaud

- One image, not three: `ghcr.io/tutunak/tgaud`, built from `Containerfile` at the repo root, context `.`
  (`images.txt`: `|.|Containerfile|`). The release scripts may stay list-driven as in echopan; a cache entry is
  not needed (the build takes a minute or two). `SOURCE_TREE` is echopan-specific: pass it only if the
  Containerfile uses it (it doesn't today; don't add a version feature).
- Branch `main`, not `master`, everywhere.
- The test jobs are tgaud's own. They are what `mise run ci` checks locally (`mise.toml`), and every one must run
  on the GitHub-hosted runner (`ubuntu-latest`), nothing skipped:
  - **tests**: `uv sync --locked`, then `uv run pytest -rs`, **with** a real PostgreSQL 18.6. The Forgejo job set
    `TGAUD_TEST_NO_DATABASE=1` only because its runner couldn't reach a service container; on GitHub the database
    tests run. The server must have what the local fixture gives it (`tests/tgaud/conftest.py`, fixture `pg`): the
    image `docker.io/library/postgres:18.6-alpine3.24`, `--memory 512m` and `SERVER_SETTINGS`, because the timing
    tests (the million-spell and 100,000-pending-probe cases) are calibrated to those limits. Setting
    `TGAUD_TEST_ADMIN_URL` skips both, and a GitHub `services:` container can't take server arguments, so don't use
    a plain service container. Either let the fixture start the server itself (podman on the runner), or start it
    in a step with the same image, memory cap and settings and point `TGAUD_TEST_ADMIN_URL` at its bootstrap
    superuser (not a CREATEROLE+CREATEDB login: it can't `CREATE DATABASE ... OWNER` the tenant). When a step
    starts the server, the job checks before pytest that the cap and two or three of the settings are in effect;
    when the fixture starts it, the fixture applies them itself. Check whether psql must be on the
    runner's PATH or the conftest falls back to podman. uv `0.11.16` as pinned in `mise.toml` and the
    Containerfile. Python: `.python-version` and `mise.toml` say 3.15, the Containerfile runs 3.13, the Forgejo job
    ran 3.13: pick one, keep `uv sync --locked` working, and say which and why.
  - **container**: the checks of `mise run image-test` and `scripts/container-e2e.sh` (the image run the way the
    deploy role runs it: `--selfcheck` offline with a read-only root, migrate twice, serve, `/health`, SIGTERM).
    Both use podman, and `container-e2e.sh` uses pasta with `--map-host-loopback`, which needs a recent podman and
    passt. **Unverified**: whether the podman on GitHub's `ubuntu-latest` image supports that. Find out from
    GitHub's `actions/runner-images` documentation (the Ubuntu image's software list), and choose: use the runner's
    podman, install a newer one, or run the job in a way that works there. Don't weaken what the checks assert,
    and keep `mise run ci` working locally (podman 5.8 here). Say in your result what you could not verify, since
    only a real GitHub run proves it; the conductor pushes the branch and watches that run.
  - **release-scripts**: `scripts/release/test-release.sh` ported to tgaud (a throwaway `registry:2` and git repo,
    Docker), covering every case echopan's covers, with echopan's semantics: the remote git tag is the commit
    point of a release, and an `X.Y.Z` image tag without a git tag is a stopped run's leftover that the next
    release reuses. Among the cases: publish skips an existing tag, stops on a registry error; release retags by
    manifest without a pull, keeps the version a commit already has (git tag on it), takes the highest remote
    `X.Y.Z` plus one patch, 1.0.0 first, stops when the image of the tree is missing; an interrupted release (the
    git tag push fails after the retag) retried at once takes the same number, retried after another commit
    released that number takes the next one and leaves the other release intact. The image a version tag points to
    has the same top-level digest as the tree tag it came from: assert that on a tree tag pushed the way
    `publishing` pushes it (the gated build below).
  - **Promotion keeps the digest.** `docker buildx imagetools create` wraps a single-manifest source in a new
    index by default (`--prefer-index=true`), which changes the digest. Use `--prefer-index=false` (or whatever
    keeps the source's top-level digest for the format `publishing` actually pushes), and check it in the test
    above.
  - **lint**: actionlint on the workflows. Optional: hadolint on `Containerfile` at `failure-threshold: warning`,
    as echopan's `lint-docker` does, only if the current Containerfile passes it unchanged.
- **The published image passes the gate before its tag exists.** The Forgejo job ran the image it was about to
  push with `--selfcheck` (`--network=none --read-only --tmpfs /tmp --cap-drop=all
  --security-opt=no-new-privileges`, exactly one `selfcheck ok: ` line) and pushed only after that passed. Keep
  that guarantee for the image `publishing` pushes: build it, run that gate on the build output, then push the
  tree tag. A podman-built image passing in another job doesn't count, since it isn't the pushed one.
- **Same build context for both builders.** BuildKit reads `.dockerignore`, not `.containerignore`. Give the
  buildx build the exclusions `.containerignore` has (for example `Containerfile.dockerignore` or `.dockerignore`
  with the same lines; say which, and how the two are kept equal, such as a test).
- Remove `.forgejo/workflows/ci.yml`: the repo no longer runs on Forgejo. Three tests read it:
  `tests/tgaud/test_containerfile.py` `test_ci_uses_no_actions_and_pushes_only_from_main`,
  `test_ci_gate_runs_the_published_image_before_the_push` and `test_ci_database_tests_are_skipped_only_on_the_runner`.
  Replace them with tests of the same kind on the new workflows (images pushed only by `publishing` on
  `pull_request`, after every test job; the gate runs on the pushed build before the push; the database tests are
  not skipped in CI; `release.yml` pushes no image build), don't just delete them. Update the docstring in
  `tests/tgaud/conftest.py` that mentions the Forgejo job.
